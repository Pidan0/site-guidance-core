# 产品目标与能力重新评估

## 用户真正要得到什么

一个可放入GitHub、在不同项目反复使用的建站核心。它能依据确认过的用户需求指导合适的建站方式，并让执行者清楚知道：可以马上做什么、还缺什么、如何补、什么证据才算完成。

## 对原有方案的重新评价

| 原有内容 | 实际能力 | 缺口 |
|---|---|---|
| 调研手册与易读HTML | 帮助理解产品、价格和技术选择 | 不能直接驱动需求判断和实施 |
| 既有业务插件 | 有模板生成、多语言和基础检查；部署路径依赖宿主 | 输入模型偏外贸产品，尚缺通用需求判断、持久化编辑与版本交付 |
| 公开产品和开源方案 | 可作为外部实施候选 | 名字、介绍和许可证不等于已接好对应业务能力 |

本仓库独立实现缺失的公共层，保留对现有宿主的接口适配可能，不复制其内部源码。原插件对不同语言的既有实现不自动成为本仓库能力：本地渲染先覆盖中文、英文；其他语言明确进入扩展项。

## 产品结构

1. 需求层：原话、确认过的目标与约束、关键追问。
2. 判断层：路线规则、选择理由、冲突、候选方案。
3. 能力层：实现、外部接入、人工验证、计划项各有状态。
4. 执行层：本地静态渲染，或读取对应外部接入流程。
5. 交付层：资料源、构建、版本、核对、回退与交接。

单次产出的指导结果包括机器可读JSON和人可读Markdown，不需要每次重新读整份市场报告。

## 0.1.0的完成范围

需求可以进入规则引擎，得到可解释路线；本地适用需求能走完资料、生成、修改、版本、检查和交接；不适用的需求有明确缺口、实施指引和验收。发布准备与真实公网发布分开。这个范围有行为测试，不靠“功能规划”代替代码。

尚不包括在线多人协作、拖拽画布、真实表单服务、支付、库存、票务、预约或账号后台。这些通过能力目录和guide保留为明确接入对象。
